# Dependency and Toolchain Currency

Recurring process for keeping rustc, tooling, and dependencies close to
latest stable. Motivation: the project has repeatedly hit "upgrade became
too hard" bottlenecks from letting deps go stale; staying near latest is
cheaper than catching up. This is the scheduled, whole-tree application of
review ruling D-17 ("upgrade everything to latest first, then apply
workarounds").

## Cadence

Run the audit (step 1) monthly. Run the full pass (steps 1-3) whenever the
audit shows meaningful drift, and always before a large feature push that
touches many crates.

## Step 1 - Currency audit ("how far behind are we?")

Record results in a dated section of the tracking issue/plan file for the
run.

- **rustc**: compare `rust/rust-toolchain.toml` `channel` against the
  latest stable release (`rustup` / https://releases.rs). Note the gap in
  releases and weeks.
- **Tooling**: sqlx-cli, cargo-deny, cargo-outdated, cargo-edit - compare
  installed vs latest.
- **Dependencies, direct + transitive**:
  `cargo outdated -R --depth 2` (deepen if a duplicate cluster is under
  investigation). `-R` recurses workspace members; `--depth 2` includes
  transitive deps. Classify each as semver-compatible (free via
  `cargo update`) or major (needs manifest bump + possible code changes).
- **Advisories**: `cargo deny check advisories`.
- **Duplicate versions**: `cargo tree -d` - list the duplicate clusters and
  their root causes (usually third-party pins we do not control).

## Step 2 - Breakage assessment ("how much breaks if we upgrade everything?")

On a throwaway branch, nothing merged:

1. Bump the rustc pin in `rust/rust-toolchain.toml` to latest stable.
2. `cargo upgrade` (cargo-edit) to bump every manifest requirement to
   latest, including majors.
3. `cargo update`.
4. `bash scripts/rust-test.sh`.

Record: what compiled, what broke, grouped by crate. The branch is
evidence, not a deliverable - discard it. Note: some deps may require a
newer rustc than the current pin; that is signal for step 3, not noise -
rustc leads the upgrade order.

## Step 3 - Follow-up task definition and prioritisation

Turn the step-2 breakage list into small, individually gate-verified
commits, in this order:

1. **rustc pin bump** - lands first; unlocks deps that require a newer
   toolchain. Gate alone.
2. **Advisory/security-driven bumps** - anything `cargo deny` flags.
3. **Framework majors** - leptos, axum, tower/tower-http, sqlx, kube,
   resend, svix: one commit per crate family, gate after each.
4. **Semver-compatible sweep** - `cargo update` within existing
   requirements; usually free, one commit.
5. **Tail majors** - remaining small crates, batched by blast radius
   (leaf libs together, game crates together), gate per batch.

Finish with a duplicate-version re-audit (`cargo tree -d`): record which
clusters resolved and which remain third-party-pinned (monitor only).

## Standing rules

- One bump (or one batch) per commit; `bash scripts/rust-test.sh` must pass
  before each commit.
- Cargo.lock is only ever regenerated by cargo, never hand-edited.
- If a bump needs code changes beyond trivial API adaptation, it becomes
  its own plan - do not fold it into a batch.
- Duplicate versions caused by third-party pins are accepted and monitored;
  do not pin our own crates *back* to dedupe (contradicts the stay-latest
  direction).
